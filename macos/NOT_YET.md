# Not on Mac yet

Generated by `tools/mac/gen-not-yet.py` from the sources. Do not edit by hand; run the script again.

Every address hash that Codeware or the RED4ext SDK asks for and that has no macOS address yet. On macOS each of
these resolves to a compile-time trap stub (`macos/MacTrap.cpp`, table `macos/MacTrapTable.inc`). The first call
logs `[cw] not on Mac yet: <name> (hash <n>) called from <image>+0x<offset>` and returns zero; a data hash reads
as zeros. The hooking driver refuses to hook a trap, so a feature whose hook target is missing is skipped with a
log line instead of patching a stub.

reach.

the declaring header when it uses the wrapper itself); for an SDK function it is every file that names both the

## Upstream (Windows) findings

Found while checking the Mac port against the 2.3.1 executable (Steam build 20383525). They are candidates for an upstream
issue; the Windows values in this fork are NOT changed, and whether to file an issue is decided at publish time.

1. **`Raw::MappinSystem::GetPoiMappinPhase` uses vtable offset 0x3C8; the function that reads the phase is at 0x430.** In the
   2.3.1 Windows executable the slots 0x3C0 and 0x3C8 of `gamemappinsIMappinSystem` are flag-setter thunks (`movzx r9d,r8b;
   mov r8b,1|2; jmp 0x1D1C650`, they lock this+0x168 and set a bit on a mappin). The slot that returns the phase is 0x430
   (Windows 0x695EC8: map lookup on this+0x110, default result 5). Evidence: the body, and the game call site Windows 0x695C88
   that calls `[rcx+0x430]` and compares the result with 5, with its Mac twin 0x2F09618 (`[x8,#0x438]`, `cmp w0,#5`). The Mac
   binding uses 0x438. The R21 read-only matcher found it; the Windows 0x3C8 may be right for another game build.
2. **The slot comments in the SDK headers for `gameIDynamicEntityIDSystem`, `gameIPopulationSystem` and `gameIPersistencySystem`
   are 8 too low.** They start the first derived virtual at 0x1A8, but `IGameSystem` already ends with `OnUninitialize` at 0x1A8
   (it declares `OnInitialize` at 0x1A0), so the first derived virtual is Windows 0x1B0. Checked in all three Windows vtables:
   `OnUninitialize` is at 0x1A8. The slots the compiler uses are right (they come from declaration order); only the comments
   mislead anyone who binds a virtual by number. Example: `IPersistencySystem::GetPersistentState` is Windows 0x1B0 (0x217908),
   comment 0x1A8.
3. **Two rows of the Windows address table point at the wrong function.** `VehicleGarageComponent_LoadSummonSetup` (hash
   1159928678, table value 0x126DF78) is a static RTTI type getter; the function that reads the `Vehicle.summon_setup` flats is
   0x126BF78 (0x2000 lower). `CNamePool_AddCString` (hash 4292220681, table value 0x2228C98) is an unrelated vtable slot (a
   `HasName`-like method of another class); the SDK function it names is inlined in the executable (CString to StringView, then the
   name adder at Windows 0x28A6CC), so no row is correct for that hash.
